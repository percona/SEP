Task execution requests are now encrypted at rest: the submitted command line (`meta.args`), the serialised task configuration an app rendered from its form (`meta.config`), and the payload of every `taskhistory` row are stored as ciphertext in the tasks database, and a tasks-track migration re-encrypts existing rows at upgrade. Coverage is those three leaves by name — every other key under `meta` is deliberately left plaintext so it stays queryable, so a task that records a credential under some other key is not covered by this change. Two copies of the same values also sit outside it and remain in the clear: the `args` and `config` an app writes onto the parent task row (`task.data`), which dispatch merges into the execution request, and whatever the Celery result backend retains until its own result TTL expires. Encrypting those is separate work, so a raw dump of the tasks database can still yield a credential by that route.
A row those values cannot be read back from — after an `ENCRYPTION_KEY` change, or a restore carrying rows another key wrote — is now reported rather than published or executed: the task-history API answers **200** with the affected value serialised as `null` and its dotted path listed in a new `unreadable_request_leaves` field, the ATW execution history shows the arguments as withheld rather than as none recorded, and dispatching that execution is refused up front, recording it as **failed** with a `failure_reason` naming the unreadable leaves and `ENCRYPTION_KEY` instead of sending ciphertext to the executor. The stored value is left untouched, so restoring the original key makes the row readable again.
