The PMM side-car's Celery worker now starts 4 prefork processes instead of one per host CPU, which bounds the PostgreSQL connections it can hold on hosts with more than four cores and raises the child count on smaller ones; this takes effect when the container is recreated from a new image. Its baked settings also pin the database pool at the current defaults of 3 connections plus 2 overflow with a 10-second timeout, so that a later change to those defaults cannot move the side-car's budget — no pool sizing changes today. Set CELERY__WORKER_CONCURRENCY to change the worker count, which is now read as an integer instead of failing the worker at startup. A bind-mounted settings.yaml keeps whatever it sets. Standalone deployments still start one worker child per CPU, since no standalone profile sets the key — but the integer coercion reaches them too, so a standalone worker given CELERY__WORKER_CONCURRENCY now starts rather than failing.
