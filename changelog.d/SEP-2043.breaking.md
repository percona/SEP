A MySQL restore whose encryption declaration disagrees with its backup type is now rejected with a 422 instead of being accepted. Three shapes are affected: an AES-256 key file named without declaring an AES-256 or dual encryption format, an AES-256 or dual format declared without naming a key file, and an AES-256 or dual format declared for a Mydumper or Binlog restore. API clients have to declare the encryption format matching the backup they are restoring and name the key file that format reads; stored restores carrying any of the old shapes are repaired when the edit form is served, so no existing task is left unopenable.
