PostgreSQL-backed deployments now open far fewer database connections. Under normal concurrent use they had been exhausting the database server's connection limit, which intermittently returned HTTP 500 across all three sub-applications. Each engine now defaults to POOL_SIZE=3, MAX_OVERFLOW=2 and POOL_TIMEOUT=10.0 instead of SQLAlchemy's 5, 10 and 30 — a threefold cut in what a single engine can hold — and a database capacity refusal now returns HTTP 503 rather than 500. This bounds each engine rather than the deployment total: the Celery worker's pool is replicated once per prefork child, so the worker's share still scales with the host's CPU count, and a many-core host may still need that concurrency capped. SQLite deployments keep the engine they build today; the pool settings are ignored there, so an install that had set one against SQLite no longer has it applied. A deployment that configured only one of the three pool settings now inherits the new defaults for the other two, so set them explicitly to keep the previous values.
